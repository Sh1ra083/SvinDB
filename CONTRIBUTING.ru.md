# Как помочь SvinDB

[English](CONTRIBUTING.md) · **Русский**

Спасибо, что хотите помочь. SvinDB — ранний прототип, и именно сейчас взгляд со
стороны особенно ценен. Чтобы помогать, не обязательно писать на Rust.

## Чем можно помочь

- **Протестировать** на своих данных и рассказать, что получилось: что
  сработало, что было медленно, что сломалось. Честные отчёты вида «у меня не
  заработало» очень нужны.
- **Сообщить об ошибке** или о недостающей возможности через issue на GitHub.
- **Исправить или перевести документацию.** Справочная документация в `docs/`
  пока на русском; английские переводы — отличный первый вклад.
- **Добавить тест** на случай, который ещё не покрыт.
- **Взять пункт из раздела «Известные ограничения»** в [README](README.ru.md) и
  заняться им. Для чего-то крупного сначала откройте issue, чтобы договориться о
  подходе до того, как вы потратите неделю.

## Как сообщить об ошибке

Откройте issue и укажите:

- версию или коммит (`svindb --version` или `git rev-parse HEAD`);
- операционную систему;
- команду, которую вы запускали, и конфигурацию;
- самый маленький запрос, документ или файл, на котором ошибка повторяется;
- что вы ожидали и что произошло на самом деле.

Не вставляйте реальные данные клиентов и учётные данные. Проблемы безопасности
отправляйте через приватный канал из [SECURITY.md](SECURITY.md), а не в
публичный issue.

## Как предложить изменение (pull request)

*Pull request* — это предложение влить ваше изменение в проект. Автор проекта
просматривает его, может попросить поправить, а затем сливает. Шаги:

1. **Сделайте форк:** нажмите **Fork** вверху справа на странице GitHub. Это
   создаст вашу личную копию.
2. **Склонируйте** свою копию и создайте ветку под изменение:

   ```bash
   git clone https://github.com/<ваше-имя>/SvinDB.git
   cd SvinDB
   git switch -c короткое-имя-изменения
   ```

3. **Внесите изменение.** Держите его узким: один pull request — одна цель.
4. **Проверьте** перед отправкой:

   ```bash
   cargo fmt --all
   cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
   cargo test --workspace --locked --all-features -- --test-threads=1
   ```

   Полный прогон тестов на ноутбуке занимает много времени. Для небольшого
   изменения достаточно запустить тесты рядом с ним, а остальное проверят
   автоматические проверки на GitHub.
5. **Сделайте коммит и отправьте ветку:**

   ```bash
   git add -A
   git commit -m "Одной строкой: что делает изменение"
   git push -u origin короткое-имя-изменения
   ```

6. **Откройте pull request:** сразу после отправки GitHub покажет на вашем форке
   кнопку **Compare & pull request**. Опишите, что вы изменили, зачем и как
   проверили.

Если что-то в этом списке непонятно, откройте issue или черновой pull request и
спросите. От вас не ждут безупречного знания git.

## Каким должно быть хорошее изменение

- Оно делает одну вещь и объясняет, зачем.
- К нему приложен тест, если меняется поведение.
- Всё, что SvinDB не поддерживает, остаётся **явной ошибкой**. Непонятный запрос
  или настройка никогда не должны молча превращаться в более слабые.
- В нём нет секретов, реальных персональных данных и путей конкретной машины.
- Числа в утверждениях о скорости и размере получены командой, которую может
  повторить другой человек (см. [`tools/bench_vs_es.py`](tools/bench_vs_es.py)).

## Измерения и профилирование

Для каждого сравнения сохраняйте одинаковыми коммит, release-профиль, seed корпуса, число документов, размер пачки, heap, ограничения машины и режим refresh. Проверяйте приём в 1, 4 и 8 потоков, оба режима `--refresh-mode disabled` и `--refresh-mode default`, с `--auto-id` и без него. JSON результата содержит фактические настройки обоих серверов до приёма и после восстановления обычного refresh. В режиме auto-ID чтение по ID исключается и из отдельного сценария, и из смешанной нагрузки. Корпуса, JSON результатов, профили и вывод Criterion храните вне checkout.

```bash
export ARTIFACTS="${TMPDIR:-/tmp}/svindb-profile"
mkdir -p "$ARTIFACTS"
CRITERION_HOME="$ARTIFACTS/criterion" cargo bench -p svindb-core --locked --bench hot_paths
python3 -m unittest discover -s tools -p 'test_bench_vs_es.py'
```

На Linux установите `cargo-flamegraph` отдельно и обеспечьте доступность `perf`. Ядро должно разрешать профилирование вашего процесса; при необходимости это разрешение предоставляет администратор. Соберите тот же release-профиль с символами, запустите обычную детерминированную нагрузку в другом терминале и снимите профиль сервера:

```bash
CARGO_PROFILE_RELEASE_DEBUG=1 cargo build --release --locked -p svindb-server
# Запустите сервер с измеряемыми настройками, затем:
cd "$ARTIFACTS"
timeout --signal=INT 30s flamegraph --pid "$SVINDB_PID" --output server.svg
```

Вместе с профилем сохраните команду, коммит, ОС/ядро, CPU, ограничения CPU/памяти и файловую систему хранилища. Цена долговечности на Linux и macOS различается: Rust `sync_all` на macOS использует `F_FULLFSYNC`, поэтому приём на разных ОС — отдельные эксперименты. Микробенчмарки изолируют вычислительные пути; они не доказывают сквозную производительность и долговечность.
