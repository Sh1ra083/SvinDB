# ADR-0002: один узел — один индекс

Дата: 2026-08-15. Состояние: **заменено ADR-0003**.

Это решение сохраняется как историческое объяснение старого одноиндексного
контракта. После требования полноценного multi-index оно заменено
[ADR-0003](0003-multi-index-runtime.md). Прежний runtime теперь выбирается
автоматически только для существующего непустого legacy-каталога либо явно
через `--single-index`; новый каталог по умолчанию многoиндексный.

## Вопрос

В пути запроса можно назвать индекс: `/мойиндекс/_bulk`. Форма привычна клиентам
Elasticsearch, и узел её принимает. Делать ли за ней настоящий multi-index —
каталог индексов, алиасы, посхемные настройки, квоты, жизненный цикл и
посиндексные метрики?

## Что было на самом деле

Имя принималось **и выбрасывалось**. Поле `Route::index` разбиралось, помечалось
`dead_code` и не читалось ни одним обработчиком.

Значит `/заказы/_bulk` и `/пользователи/_bulk` писали в один и тот же индекс.
Молча. Клиент, разделивший данные по именам, узнавал об этом не отказом, а тем,
что его запрос находит чужие документы, — и узнавал когда-нибудь потом.

Такое поведение нарушает изоляцию наборов данных, заявленную формой URL.

## Решение

**Multi-index не делаем. Контракт «один узел — один индекс» объявлен и
проверяется.**

Довод не в трудоёмкости. Довод в том, что multi-index здесь **дублировал бы уже
выбранный способ делить данные**. Узел устроен как один индекс по всей глубине:
один писатель под одним замком, один список сегментов, один журнал, одна схема,
один каталог идентификаторов. Множество индексов внутри такого узла означало бы
столько же копий всей этой машины — то есть то же самое, что несколько узлов, но
с разделяемым отказом и без выигрыша.

Делить данные в SvinDB и так есть чем: **шарды** внутри процесса и **карта
кластера** по сети (ADR-0001). Кому нужны раздельные наборы документов — это
раздельные узлы или раздельные шарды, а не второе измерение внутри одного узла.

## Что сделано вместо

1. **Требуется постоянство имени, а не совпадение с чем-то.** Узел запоминает
   имя, под которым к нему обратились первый раз, и дальше принимает только его.
2. **Второе имя — отказ `404`**, называющий оба: и то, под которым уже
   обращались, и запрошенное.
3. **`_all` и `*` принимаются всегда**: для узла с одним индексом они верны
   буквально.
4. **Координатор имён не проверяет.** Своих данных у него нет; шарды проверят
   сами и по своим именам, а не по его.

### Почему постоянство, а не имя каталога данных

Первая попытка требовала, чтобы имя из пути совпадало с последней частью
каталога данных. Это проще и **хуже**: каталог называет оператор для себя,
клиент его не знает, и совпадать они не обязаны ничем. Такое правило сломало бы
всякого совместимого клиента, не поймав ни одной настоящей ошибки.

Поймал это гейт: существующая проверка раскодирования идентификатора обращается
к `/сообщения/_doc/...`, и привязка к каталогу её отвергла.

Узлу безразлично, **как** зовут его единственный индекс — различать нечего.
Вредны ровно два разных имени на один узел, и проверяется теперь именно это.

Форма пути сохранена: совместимые клиенты работают как работали. Убрано только
ложное ожидание.

## Цена, которую платим

Клиент, сегодня пишущий в один узел под **несколькими** именами, получит `404` на
втором из них. Это **намеренно**: он уже писал не туда, куда думал, и отказ
говорит ему об этом сразу, а не после того, как выдача смешает два набора
документов.

Клиент, использующий одно имя — любое, — не заметит ничего.

## Ограничения прежнего контракта

Алиасы, квоты и посиндексные метрики не заведены и заводиться не будут, пока
стоит этот контракт: у одного индекса алиас — это второе имя одному и тому же,
квота — это квота узла, а посиндексная метрика — это метрика узла. Всё три
существуют, просто без слова «индекс» в названии.
