# ADR-0003: независимые индексы в одном процессе

Дата: 2026-08-16. Состояние: **принято**. Заменяет ADR-0002 для обычного
локального запуска.

## Контекст

Одноиндексный HTTP-узел принимал имя в пути только ради совместимости клиента.
У него действительно были один writer, один WAL, одна schema и один состав
сегментов. Такой контракт безопасен, пока он явный, но не решает обычную задачу
Elasticsearch: держать рядом `orders`, `users`, `logs-*` с разными схемами и
жизненным циклом без отдельного процесса и порта на каждый набор.

Просто перестать проверять имя нельзя. Это вернуло бы старый дефект, когда
`/orders/_bulk` и `/users/_bulk` молча писали в один каталог. Нельзя также
положить общий WAL поверх нескольких схем: replay перестал бы однозначно знать,
каким индексатором применять подтверждённую запись.

## Решение

Сделать multi-index обычным режимом `serve <root> <port>` для нового каталога.
Корень получает версионированный marker, каталог `indices/` и отдельный runtime
на каждое имя.
Единицей маршрутизации становится целый `Arc<Node>`:

- live-снимок сегментов;
- writer и его индексатор;
- WAL и checkpoint;
- schema и settings;
- writer-lock;
- refresh/rescan/maintenance;
- счётчики и snapshot source.

Ни одна из этих частей не выбирается отдельно. Получив `Node`, запрос уже не
может обратиться к данным другого имени.

Переход определяется по дисковому состоянию, а не по включающему флагу:

- отсутствующий или пустой каталог становится multi-root;
- каталог с multi-marker открывается как multi-root;
- существующий непустой одноиндексный каталог автоматически открывается
  прежним runtime без миграции;
- служебные каталоги multi или crash-tail первой записи marker без самого
  marker направляются в fail-closed multi recovery, а не в legacy writer.

`--single-index` остаётся явным средством создать новый каталог старого формата
для embedded/диагностических сценариев. Применить его к multi-root нельзя.
Старый `--multi-index` временно принимается как совместимый no-op, но не является
частью нормального запуска.

## Долговечный lifecycle и catalog format 2

Имя проверяется до обращения к файловой системе и кодируется в hex UTF-8.
Метаданные внутри каталога повторяют исходное имя и версию layout; discovery
сверяет оба представления.

CREATE сначала строит `.creating/<unique>`, синхронизирует metadata/schema/
settings и публикует каталог атомарным rename. В процессную карту runtime
попадает только после успешного открытия и WAL recovery.

DELETE сначала удаляет имя из карты, поэтому новые запросы его не получают.
Уже начатые запросы держат `Arc<Node>` и завершаются на прежнем поколении.
После последнего `Arc` останавливаются фоновые потоки, освобождается writer-lock,
каталог атомарно переносится в `.trash`, после чего удаляется. Если питание
пропало после rename, restart дочищает trash; если до rename, не подтверждённый
DELETE не считается состоявшимся и индекс снова открывается.

Root имеет отдельный `flock`: locks дочерних индексов не защищают от двух
процессов, одновременно создающих разные имена в одном каталоге. Writable
процесс берёт эксклюзивный lock, read-only процессы — совместный. Поэтому
несколько читателей разделяют стабильный каталог, но lifecycle-писатель не
может удалить и пересоздать индекс под процессом, продолжающим отдавать старое
поколение.

Начиная с 1.3.0 листинг `indices/` больше не является источником логического
состава. UUID, open/closed state, blocks, tags/descriptions и aliases лежат в
корневом catalog snapshot + checksum-framed WAL с монотонным generation.
Транзакция сначала проходит полную проверку, затем append+fsync и только потом
публикуется как новый immutable `Arc<Catalog>`. Оборванный последний frame
отбрасывается; checksum-разрыв с целой записью после него считается порчей в
середине и останавливает запуск.

CREATE использует durable `Creating`, а финальная запись публикует открытый
runtime и aliases вместе. DELETE/remove_index сначала исключают UUID и его
привязки из catalog, а физический каталог дочищается после завершения старых
`Arc`. Close/open используют переходные `Closing`/`Opening`, чтобы crash мог
однозначно откатить незавершённый переход в безопасное состояние.

UUID записываются рядом с физическими индексами, durable catalog создаётся до
повышения marker до format 2. Бинарник, знающий только format 1, обязан
отказаться от открытия: иначе он открыл бы архивный writer, проигнорировав
aliases и write blocks.

## Ресурсная модель

Сегменты и WAL принадлежат индексам, но RAM, CPU, mmap и файловые дескрипторы —
процессу. Поэтому:

1. query pool и inflight body budget общие;
2. автоматический ingest budget делится между writer'ами, явные `flush_mb`
   резервируются до деления остатка; живое изменение settings проходит под
   тем же lock, что CREATE/DELETE, и повторяет проверку до записи на диск;
3. eager warm использует один последовательный бюджет;
4. тяжёлые merge разных индексов идут через одну процессную полосу;
5. `--max-indices` задаёт управляемый предел одновременно открытых runtime'ов
   (64 по умолчанию), а не предел дискового формата.

Так большое число маленьких индексов деградирует контролируемо: создание
получает понятный отказ или меньший буфер, а не OOM, исчерпание потоков или
молчаливое смешение данных.

## API и совместимость

Добавлены `PUT|GET|HEAD|DELETE /{index}` и `GET /_cat/indices`. Все data-plane
пути в multi-режиме требуют имя. Создание принимает родной `fields` либо
проверяемое подмножество Elasticsearch `mappings.properties`. Неподдержанная
семантика отвергается: молчаливо проигнорированный analyzer хуже явного `400`.

Приёмник снимков общий только как разрешённый корень. Фактические архивы
разнесены по `svindb-indices/i-<hex имени>`, поэтому `orders/daily` и
`users/daily` — два независимых снимка, а чтение одного индекса не перечисляет
снимки другого.

Aliases, `*`, `_all` и список индексов поддержаны для локального search.
Resolver фиксирует один catalog generation и дедуплицирует физические UUID.
При совместимой schema/mapping их immutable сегменты собираются в один
виртуальный `Segments`, поэтому top-K, sort, vector/hybrid и aggregations
выполняют обычный глобальный reduce движка. Ответ по первому индексу или сумма
локальных cardinality запрещены.

Запись через alias идёт в один `is_write_index`; wildcard/list/_all для записи
отвергаются. Общий корневой NDJSON bulk, в котором разные строки называют
разные `_index`, остаётся отдельной будущей возможностью: ему нужны
посиндексные backpressure и item-level ответы. Индексный NDJSON bulk проверяет,
что metadata `_index` согласуется с целью пути, и отказывает при расхождении.

Сетевые `--shards/--replicas` пока несовместимы с multi-root. Их общая карта не
имеет измерения index и направила бы разные имена в один fanout. Они будут
совмещены только вместе с посиндексным cluster-state, а не условным ветвлением
URL.

## Последствия

- Несколько локальных индексов используют один порт, auth/CORS, worker pool и
  процессные бюджеты, оставаясь физически и семантически раздельными.
- Один повреждённый опубликованный индекс останавливает старт процесса. Это
  выбранный fail-closed договор: тихо поднять неполный каталог хуже явного
  отказа с именем индекса.
- Удаление может ждать долгий уже начатый запрос или merge. Ответ означает
  настоящее закрытие и освобождение lock, а не поставленную в память заявку.
- Предел 64 — безопасное умолчание, меняемое оператором. Универсальность даёт
  не отсутствие пределов, а явный, измеримый и настраиваемый предел без
  зависимости дискового формата от конкретного стенда.
