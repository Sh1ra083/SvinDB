# API SvinDB

Этот документ описывает публичный HTTP- и CLI-контракт текущей версии SvinDB.
Внутренние форматы и потоки исполнения вынесены в
[ARCHITECTURE.md](ARCHITECTURE.md).

## Общие правила HTTP

- По умолчанию узел слушает `127.0.0.1:19300`.
- Тела запросов и ответов используют JSON в UTF-8.
- Для непустого тела `POST`, `PUT`, `PATCH` и `DELETE` обязателен
  `Content-Type: application/json`.
- Ошибка возвращается объектом `{"error":"описание"}`.
- Неизвестные маршруты закрыты авторизацией так же, как маршруты чтения.
- `GET /_health` и `GET /{индекс}/_health` намеренно доступны без учётных
  данных; `GET /{индекс}/_metrics` требует право `read`, если авторизация
  включена.
- Поддерживаются keep-alive, ограничения размера заголовков и тела, таймауты
  чтения и записи. Неоднозначное сочетание `Content-Length` и
  `Transfer-Encoding` отвергается.

### Маршруты

Новый каталог по умолчанию является корнем нескольких индексов. В таблице
`/{индекс}` обязателен для операций с данными и состоянием конкретного индекса.
Автоматически распознанный legacy-каталог принимает те же маршруты без этого
первого сегмента. Корневые `/_health`, `/_stats`, `/_cat/indices` и
`/_security` относятся ко всему процессу; их нельзя подменять именем индекса.

| Метод и путь | Назначение | Требуемое право |

| `GET\|HEAD /{индекс}` | описание или проверка существования индекса | `read` |
| `DELETE /{индекс}` | безопасно закрыть и удалить индекс | `admin` |
| `GET /_cat/indices` | каталог индексов процесса в JSON | `read` |
| `GET /_cat/aliases` | каталог alias → physical index | `read` |
| `POST /_aliases` | атомарный пакет add/remove/remove_index | `admin` |
| `GET\|HEAD /_alias/{alias}` | описание или проверка alias | `read` |
| `GET /{индекс}/_alias` | aliases физического индекса | `read` |
| `PUT\|DELETE /{индекс}/_alias/{alias}` | добавить или снять привязку | `admin` |
| `POST /{alias}/_rollover[/{новый}]` | создать поколение и переключить writer | `admin` |
| `GET\|PUT /{индекс}/_metadata` | описание и теги индекса | `admin` |
| `GET /{индекс}/_blocks` | текущие lifecycle-блоки | `admin` |
| `PUT\|DELETE /{индекс}/_block/{block}` | добавить или снять блок | `admin` |

| `POST /{индекс}/_open` | recovery и публикация runtime | `admin` |

| `POST /{индекс}/_delete` | удалить документы по `id` | `write` |

### Индексы по умолчанию

`svindb serve <корень> <порт>` создаёт layout `multi-index-v1`, если каталог
новый или пустой. Никакой плагин или включающий флаг не требуется:

```text
root/
├── multi-index-v1.json
├── catalog/
│   ├── snapshot.bin
│   └── journal.bin
├── .writer.lock
├── .creating/
├── .trash/
└── indices/
    ├── i-<hex имени>/
    │   ├── index.json
    │   ├── schema.json
    │   ├── settings.json
    │   ├── wal/
    │   └── seg.../
    └── ...
```

Имена — непустые lowercase UTF-8 длиной до 255 байт. Запрещены traversal,
разделители пути, пробелы, управляющие знаки, `, # : * ? " < > |` и первый
знак `_`, `-` или `+`. На диске имя кодируется побайтово и сверяется с
`index.json`, поэтому Unicode, разный регистр и особенности файловой системы не
могут склеить два индекса.

Пустое тело `PUT /{индекс}` создаёт схему `title:2,body:1` либо схему из
`--fields`. Родная форма принимает `fields` и необязательный объект
`settings`, `metadata` и `aliases`:

```json
{
  "fields": "message:text,price:double,created:date:iso",
  "settings": {"refresh_interval_ms": 500, "flush_mb": 128},
  "metadata": {"description":"заказы", "tags":["orders","hot"]},
  "aliases": {"all_orders":{"is_write_index":true}}
}
```

Вместо `fields` принимается полное тело создания с `settings` и
`mappings.properties` Elasticsearch. Mapping обязан явно задавать
`dynamic:"strict"` либо `dynamic:false`: значение `true`, `runtime` и
отсутствующее значение означают изменение схемы на ходу, которого SvinDB не
изображает source-only хранением.

Поддержаны `text`, `keyword`, `constant_keyword`, `short`, `integer`, `long`,
`unsigned_long` в диапазоне `i64`, `float`, `double`, `scaled_float`,
`boolean`, `date`, `binary`, `geo_point`, `dense_vector` с `dims`,
`sparse_vector`, `object` и произвольная иерархия `nested`. Компилятор также
исполняет:

- lowercase-normalizer конкретного keyword-поля; обычный `keyword` остаётся
  регистрозависимым;
- text multi-fields через `fields`;
- `ignore_above` отдельно для каждого элемента;
- `constant_keyword.value`;
- округление `scaled_float.scaling_factor` на записи и в точном запросе;
- `enabled:false` как source-only поддерево;
- `strict_date_optional_time||epoch_millis` и `...||epoch_second`;
- `index`, `store`, `boost`, `dims` и проверяемые vector-параметры.

Неизвестный тип, analyzer, normalizer или параметр даёт `400`; ни один ключ не
выбрасывается молча. По умолчанию исходный JSON хранится один раз в скрытом
compressed field-store независимо от `store` отдельных листьев. Поэтому
`store:false` сам по себе не выключает `_source`, а отсутствующие поля не
материализуются пустыми строками.
Compiled mapping сохраняется в `mapping.json`, загружается до открытия порта и
входит в snapshot/restore вместе со schema и settings.

### Отключение физического `_source`

Для нового search-only индекса исходный JSON можно не сохранять:

```json
{
  "mappings": {
    "_source": {"enabled": false},
    "dynamic": "strict",
    "properties": {
      "body": {"type": "text", "index": true, "store": false},
      "title": {"type": "text", "index": true, "store": true},
      "timestamp": {"type": "date", "index": true, "store": false}
    }
  }
}
```

Эквивалентная статическая форма:

```json
{
  "settings": {
    "index": {"mapping": {"source": {"mode": "disabled"}}}
  },
  "mappings": {
    "dynamic": "strict",
    "properties": {"body": {"type": "text"}}
  }
}
```

Режим неизменяем: он задаётся при CREATE, сохраняется в `mapping.json` и
переносится rollover/snapshot. `index:true,store:false` оставляет поле
поисковым, но не позволяет вернуть его исходное значение; `store:true` создаёт
отдельную копию для `fields`, GET, `_mget` и highlight. В режиме `disabled`
`_source` отсутствует в ответе даже при `_source:true`; запрошенное недоступное
поле отсутствует, а не превращается в пустую строку.

Highlight без source требует `store:true`. Hierarchical nested, которому нужна
точная parent-child проверка исходного JSON, получает `400`; прямые slot-запросы
сохраняют прежний путь. `synthetic`, source filtering и конфликт двух форм
source mode получают точный `400`. Переключить существующий индекс через
`/_settings` нельзя; для смены режима создаётся новое поколение и выполняется
контролируемый cutover.

Все операции с данными в этом режиме требуют имени в пути:
`/{index}/_bulk`, `/{index}/_doc/{id}`, `/{index}/_mget`,
`/{index}/_put`, `/{index}/_delete`, `/{index}/_flush`,
`/{index}/_settings`, `/{index}/_mapping`, `/{index}/_metrics` и
`/{index}/_search`. Корневые `/_health` и `/_stats` агрегируют процесс,
`/_security` остаётся процессным. Поиск принимает concrete index, alias,
`*`/`?` wildcard, `_all` и список через запятую. Физические targets
дедуплицируются, после чего движок строит единый виртуальный `Segments`:
top-K, sort, vector/hybrid и aggregations считаются по всему составу, а каждый
hit получает `_index`. Индексы с несовместимыми schema/mapping получают точный
`400`; они не разбираются по правилам первого target.

У wildcard/`_all` поиска поддерживаются параметры разрешения целей:

- `expand_wildcards=open` по умолчанию; `closed`, `all`, `none` и их допустимые
  комбинации управляют тем, какие состояния раскрывает именно шаблон;
- `hidden` принимается как совместимое пустое множество: hidden-state у SvinDB
  отсутствует, поэтому скрытых целей в каталоге быть не может;
- найденный закрытый индекс отвечает `index_closed_exception`; только явный
  `ignore_unavailable=true` разрешает его пропустить;
- `allow_no_indices=true` разрешает пустой итоговый состав и возвращает пустую
  выдачу. Без него шаблон без доступных целей получает `404`.

Точные concrete/alias имена не превращаются в wildcard и поэтому не скрывают
закрытый индекс в зависимости от `expand_wildcards`.

### Aliases, metadata и lifecycle

Пакет `POST /_aliases` применяется целиком на одном generation:

```json
{
  "actions": [
    {"add":{"index":"messages-000001","alias":"all_messages"}},
    {"add":{"index":"messages-000002","alias":"all_messages","is_write_index":true}},
    {"remove":{"index":"obsolete","alias":"old_messages","must_exist":true}}
  ]
}
```

`remove_index` удаляет физические targets и их привязки той же catalog-
транзакцией. Alias не может совпадать с именем индекса или указывать на другой
alias. У multi-target alias допускается ровно один явный
`is_write_index:true`; у единственного target отсутствие признака означает
неявный writer, а явное `false` запрещает запись. Wildcard, `_all` и список не
являются целью записи. GET/MGET по alias с несколькими targets получают `400`
как неоднозначные.

Rollover выполняется принудительно при пустом теле либо по `max_docs`,
`max_age`, `max_size`:

```json
{
  "conditions":{"max_docs":1000000000,"max_age":"30d","max_size":"500gb"},
  "dry_run":false,
  "settings":{"refresh_interval_ms":500},
  "metadata":{"description":"новое поколение","tags":["messages","hot"]}
}
```

Без явного имени `messages-000001` превращается в `messages-000002`. Schema,
mapping и settings клонируются; metadata копируется и может быть переопределена.
Новый индекс открывается до публикации. Затем одной записью он становится
writer, старый получает `write` block, и только после fsync приходит ACK.

`PUT /{index}/_metadata` — частичный patch: отсутствующее поле не меняется,
`description:null` очищает описание, `tags:[]` очищает теги. Описание — до
8 КиБ UTF-8; тегов до 64, каждый 1–128 байт, общий record до 16 КиБ. Теги
уникализируются без изменения регистра. `GET /_cat/indices?tag=cold` делает
точный отбор.

Blocks складываются независимо:

- `write` запрещает изменения документов, но не поиск и административный flush;
- `read` запрещает search/GET/MGET, но не health и административные точки;
- `metadata` запрещает aliases, metadata, settings и lifecycle; снять сам этот
  блок администратор может всегда;
- `read_only` означает `write + metadata`;
- `read_only_allow_delete` запрещает данные и metadata, но разрешает физический
  `DELETE /{index}`.

`/_close` — не синоним read-only: он прекращает новые запросы, ждёт начатые,
делает durable flush/checkpoint, останавливает фоновые потоки и выгружает Node,
writer и mmap. Закрыть текущий write index alias нельзя: сначала требуется
rollover или смена writer. `/_open` выполняет recovery до публикации runtime.
Blocks и metadata переживают close/open и restart.

Root catalog хранится как snapshot плюс checksum-framed WAL. Бинарник,
не знающий формата catalog, fail-closed откажется открыть корень и не сможет
проигнорировать aliases/write blocks.

Снимки вызываются как `/{index}/_snapshot/{name}`. Внутри разрешённого
`snapshot.allow` каждый индекс получает собственный безопасный каталог
`svindb-indices/i-<hex имени>`: одинаковое имя снимка у двух индексов не
сталкивается и не может вернуть архив соседа. Ответ показывает фактический
scoped-приёмник.

Изменение `flush_mb` через `PUT /{index}/_settings` проходит под общей
процессной блокировкой: сумма двух оборотных буферов всех явно настроенных
индексов проверяется до записи settings на диск, а автоматические пределы
остальных writer'ов пересчитываются в той же транзакции. Превышение даёт
`409`, не частично применённую настройку и не будущий OOM.

Multi-root защищён процессным `flock`: один writable-процесс несовместим с
другим writer или read-only процессом на том же каталоге, а несколько
read-only процессов могут работать одновременно. Это не даёт читателю навсегда
остаться на старом поколении индекса после чужого `DELETE`/повторного `PUT`.

При запуске существующего непустого одноиндексного каталога SvinDB
автоматически выбирает прежний runtime и не переносит файлы. Флаг
`--single-index` нужен только для явного создания нового legacy-каталога или
специализированного одноиндексного стенда. Старый `--multi-index` временно
принимается как совместимый no-op для уже написанных команд, но в новых
конфигурациях не нужен.

`--shards`, `--replicas`, `--term` и `--ack` нельзя совмещать с
multi-index root: одна общая топология смешала бы маршрутизацию разных индексов.
До появления посиндексного cluster-state распределённую топологию поднимают
отдельными процессами, а локальные независимые индексы — одним multi-runtime.

## Поиск

Все виды поиска используют `POST /{индекс}/_search`. В legacy-runtime тот же
обработчик доступен как `POST /` или `POST /_search`. Ветвь выбирается по
содержимому тела:

- наличие `vector` включает поиск по плотному вектору;
- наличие `sparse` добавляет разреженный вектор к текстовому запросу;
- остальные запросы выполняются текстовым и булевым движком;
- узел с `--shards=` пересылает исходное тело шардам и объединяет их ответы.

### Два диалекта запроса

Узел принимает родной JSON и совместимое подмножество Elasticsearch. Диалект
определяется по ключам тела; смешение обоих в одном объекте отвергается, чтобы
один запрос нельзя было истолковать двумя способами.

Поддержаны Elasticsearch-условия `match`, `term`, `terms`, `range` с
`gte`/`lte`/`gt`/`lt`, одноуровневый `bool`, `exists`, `nested` и `match_all`,
а также `_source:true|false`, `size`, `from`, стандартный `sort`, `aggs`,
`search_after` и `highlight`. Расширения SvinDB передаются рядом с `query` в
объекте `svindb`:

```json
{
  "query":{"bool":{"must":[{"match":{"body":"быстрый поиск"}}]}},
  "_source":true,
  "size":20,
  "svindb":{"ids":true,"translit":true,"fields":["title","body"]}
}
```

`term` и `terms` работают по keyword, binary, boolean, целым, дробным и date с
той же нормализацией, что использовалась при записи. Ветвь `bool.filter`
исполняет term/nested с нулевым score. `minimum_should_match` поддерживает
целое число. Стандартный sort имеет форму `"field"` или
`{"field":{"order":"asc|desc"}}`.

Source filtering (`_source:[...]`/`includes`/`excludes`), `post_filter`,
`terminate_after`, `stored_fields`, вложенный `bool`,
`match_phrase` в ES-диалекте и query options, которые движок не исполняет,
получают точный `400`. Фразы доступны через `svindb.phrases`. Неизвестный
оператор или ключ не превращается в более слабый запрос. Полный список отличий приведён в
[SCHEMAS.md](SCHEMAS.md#совместимость-с-elasticsearch).

`track_total_hits: true` запрашивает точное число совпадений; положительное
целое `N` ограничивает возвращаемое значение порогом `N`. Ответ содержит
`total.value` и `total.relation`: `eq` для точного результата, `gte` для нижней
границы. Без параметра, при `false` или `0` поле `total` не возвращается.
Неполный запрос не выдаёт свой счётчик за точный. У сетевого координатора
подсчёт `track_total_hits` не поддерживается.

### Получить любые документы без условия

Эквивалент Elasticsearch `match_all` поддержан явно:

```bash
curl -s http://127.0.0.1:19300/catalog/_search \
  -H 'Content-Type: application/json' \
  -d '{"size":20,"_source":true,"query":{"match_all":{}}}'
```

Это возвращает документы без текстового условия, но не обещает случайную
выборку. Порядок детерминирован правилами текущего search/sort. Elasticsearch
`random_score` не реализован и получает строгий HTTP 400; для честной
случайной выборки клиент должен выбрать ID из известного множества или хранить
отдельное заранее рассчитанное поле случайного порядка.

### Минимальный текстовый запрос

```bash
curl -s http://127.0.0.1:19300/catalog/_search \
  -H 'Content-Type: application/json' \
  -d '{
    "k": 10,
    "words": [
      {"field": "title", "terms": ["распределённый"]},
      {"field": "body", "terms": ["поиск", "search"]}
    ]
  }'
```

`terms` внутри одного элемента — альтернативные формы одного слова. Документ
получает вклад этого слова один раз. Разные элементы `words` — независимые
слова, их вклады складываются.

Поле задаётся устойчивым именем или числовым идентификатором. Для публичных
клиентов предпочтительно имя: внутренние номера зависят от схемы.

### Параметры текстового запроса

| Ключ | Тип и умолчание | Назначение |
|---|---|---|
| `k` | целое, `10` | размер верхушки; диапазон `1..10000` |
| `words` | массив | необязательные слова, плоский синоним `query.should` |
| `must` | массив | обязательные слова |
| `must_not` | массив | запрещённые слова |
| `filter` | массив | диапазоны и проверка наличия значения |
| `query` | объект | вложенное булево дерево |
| `phrases` | массив | фразы с порядком и `slop` |
| `sparse` | объект | запрос к `sparse_vector` |
| `translit` | bool, `false` | добавить варианты раскладки и транслитерации |
| `max_expansions` | целое, `50` | query-wide предел уникально принятых prefix-форм, максимум `10000` |
| `max_expansion_examined` | целое, `10000` | query-wide предел физически просмотренных dictionary entries; `0` снимает предел |
| `max_verify` | целое | предел проверок текста для полей без позиций; `0` снимает предел |
| `timeout_ms` | целое, `30000` | общий deadline search/aggregation/hydration; `0` выбирает серверное умолчание; более строгий timeout заголовка сохраняется |
| `partial` | bool, `true` | разрешить явно помеченный bounded partial; `false` отвечает retryable 503 |
| `fields` | массив имён | вернуть сохранённое содержимое полей |
| `ids` | bool, `true` | вернуть внешний `id` документа |
| `highlight` | объект | вернуть фрагменты с подсветкой |
| `sort` | массив | сортировка по колонкам, максимум четыре ключа |
| `from`, `size` | целые | страница; сумма не больше `10000` |
| `search_after` | массив | курсор глубокой пагинации |
| `pit` | строка или объект | открыть/продлить immutable point-in-time для `search_after` |
| `routing` | строка/число | на coordinator спросить один shard по routing key |
| `aggs` | объект | агрегации, максимум 32 |

Запрос без слов, фраз и фильтров отвергается. Запрос только с фильтром законен:
он используется для выборок по времени, диапазону или наличию значения.

### Слова и префиксы

```json
{
  "field": "body",
  "terms": ["сервер", "server"]
}
```

Звёздочка поддерживается только в конце слова:

```json
{"field":"body","terms":["распредел*"]}
```

Префикс раскрывается лениво по словарям ReadView. `max_expansions` ограничивает
число уникально принятых пар «поле, форма» по всему запросу, а
`max_expansion_examined` — фактически просмотренные записи словарей. Ответ
всегда содержит `expansion.examined`, `expansion.accepted` и оба предела. Если
граница достигнута, выдача получает `partial:true`, `complete:false` и
`terminated:"expansion_budget"`; при `partial:false` сервер отвечает 503.
Пустые элементы `terms` игнорируются; полностью пустое условие не участвует в
запросе.

### Булев запрос

Плоская форма:

```json
{
  "must": [{"field":"body","terms":["индекс"]}],
  "words": [{"field":"body","terms":["быстрый"]}],
  "must_not": [{"field":"status","terms":["deleted"]}],
  "minimum_should_match": 1
}
```

Эквивалентная древовидная форма:

```json
{
  "query": {
    "must": [
      {"term":{"field":"body","terms":["индекс"]}},
      {"bool":{
        "should":[
          {"term":{"field":"title","terms":["поиск"]}},
          {"term":{"field":"title","terms":["база"]}}
        ],
        "minimum_should_match":1
      }}
    ],
    "must_not":[
      {"term":{"field":"status","terms":["deleted"]}}
    ]
  }
}
```

Вложенные узлы поддерживают `must`, `should`, `must_not` и
`minimum_should_match`. `filter` задаётся на верхнем уровне либо внутри
верхнего `query`.

### Диапазоны и наличие значения

```json
{
  "filter": [
    {"field":"timestamp","from":1700000000,"to":1800000000},
    {"field":"views"}
  ]
}
```

Условия диапазона включают обе границы. Отсутствующая граница означает
неограниченную сторону. Условие только с `field` проверяет наличие
индексируемого значения.

### Условия на элементах вложенного массива

Группа, объявленная в схеме как массив объектов, запрашивается через `slots`.
Все условия `all` должны совпасть на одном элементе массива, а не на разных:

```json
{
  "query": {
    "must": [{
      "slots": {
        "group": "reactions",
        "all": [
          {"term":{"field":"reactions.emoji","value":"👍"}},
          {"range":{"field":"reactions.count","from":10}}
        ],
        "none": [
          {"term":{"field":"reactions.hidden","value":"true"}}
        ],
        "min_count": 1,
        "boost": 1.0
      }
    }]
  }
}
```

`all` обязателен и не может быть пустым. Условие элемента поддерживает `term`,
`range` и `exists`. Фразы по полям внутри массива не поддерживаются: позиция
такого поля обозначает номер элемента, а не номер слова.

### Фразы

```json
{
  "phrases": [{
    "field":"body",
    "terms":["распределённый","поиск"],
    "slop":1,
    "boost":2.0
  }]
}
```

Во фразе должно быть не меньше двух слов. `slop` ограничен `1000`. Префиксы
внутри фразы не поддерживаются.

Если поле создано без позиций, движок проверяет кандидатов по сохранённому
тексту. `max_verify` ограничивает такую работу; при достижении предела ответ
содержит `"partial":true`.

### Разреженный вектор

```json
{
  "k":10,
  "sparse":{
    "field":"embedding_sparse",
    "query":{"поиск":1.4,"индекс":0.7}
  }
}
```

Поле должно иметь тип `sparse_vector`. Положительные веса превращаются в
взвешенные измерения запроса. Разреженный вектор нельзя сочетать с вложенным
булевым деревом или `minimum_should_match`.

### Плотный вектор

```json
{
  "k":10,
  "vector":{
    "field":"embedding",
    "query":[0.12,-0.04,0.31]
  },
  "fields":["title"],
  "ids":true,
  "source":true
}
```

Размерность запроса обязана совпадать со схемой `dense_vector:<N>`. В ответе
`score` тем больше, чем ближе документ: расстояние преобразуется в единую с
остальным API шкалу качества. `fields`, `source`, `id` и `_id` гидратируются
из атомарного source-backed документа и доступны при `store:false`. Векторная
ветвь принимает только `k`, `vector`, `fields`, `ids` и `source`; неизвестный
ключ получает HTTP 400, а не молча игнорируется.

### Географическая точка

`geo_point` принимает объект `{"lat":55.75,"lon":37.61}`, строку
`"55.75,37.61"` или массив `[37.61,55.75]`. Движок создаёт числовые поля
`<имя>.lat` и `<имя>.lon`, поэтому прямоугольная область задаётся обычными
включительными диапазонами:

```json
{
  "filter":[
    {"field":"place.lat","from":55.0,"to":56.0},
    {"field":"place.lon","from":37.0,"to":38.0}
  ]
}
```

Широта ограничена `[-90,90]`, долгота — `[-180,180]`. Нативного запроса по
радиусу, сортировки по расстоянию, полигонов и геоагрегаций пока нет.

### Сортировка и пагинация

```json
{
  "filter":[{"field":"timestamp","from":1700000000}],
  "sort":[
    {"field":"timestamp","order":"desc"},
    {"field":"views","order":"desc"}
  ],
  "size":100
}
```

Без сортировки документы упорядочиваются по релевантности и внутреннему номеру.
С сортировкой каждый hit получает массив `sort`; последним элементом курсора
всегда передаётся `doc`:

```json
{
  "search_after":[1700000123,900,4812],
  "sort":[
    {"field":"timestamp","order":"desc"},
    {"field":"views","order":"desc"}
  ]
}
```

Для выдачи по релевантности курсор содержит `[score, doc]`. Внутренний `doc`
может измениться после слияния сегментов, поэтому deep pagination открывает PIT:

```json
{
  "size":1000,
  "sort":[{"field":"timestamp","order":"asc"}],
  "pit":{"keep_alive_ms":60000},
  "match_all":true
}
```

Ответ возвращает строку `pit`. Следующая страница передаёт её рядом с курсором:

```json
{
  "size":1000,
  "sort":[{"field":"timestamp","order":"asc"}],
  "search_after":[1700000123,4812],
  "pit":{"id":"<id из ответа>","keep_alive_ms":60000},
  "match_all":true
}
```

PIT закрепляет и состав сегментов, и immutable live bitmap. TTL — от 1 до
120000 мс, process limit — 16 активных PIT, общий admission bitmap — 512 MiB.
Истёкший PIT отвечает `404` с `reason:"pit_expired"`, не переходит на текущий
ReadView. Конкретный `/{index}/_search` поддерживает PIT и в стандартном
multi-index runtime. Строго отвергаются только PIT по нескольким физическим
целям (multi-target alias, wildcard или список индексов) и vector PIT.
Долговременная ссылка клиента всё равно должна использовать внешний `id`.

### Поля, идентификаторы и подсветка

```json
{
  "words":[{"field":"body","terms":["поиск"]}],
  "fields":["title","body"],
  "ids":true,
  "highlight":{"fields":["body"],"size":240}
}
```

На source-backed индексах нового формата `fields` извлекаются из точной
source/projection и доступны независимо от `store`; legacy- и source-disabled
индекс может вернуть только физически сохранённые поля. Поля `noindex`
возвращаются при наличии source или `store:true`, но
любой поиск по ним завершается ошибкой вместо ложной пустой выдачи. В
ES-диалекте `_source:true` добавляет полный исходный объект, а `false` не тратит
время на его hydration. У source-disabled индекса полный объект отсутствует в
обоих случаях.

### Формат ответа

```json
{
  "took_ms":1.482,
  "visited":740,
  "partial":false,
  "complete":true,
  "expansion":{"examined":0,"accepted":0,"examined_limit":10000,"accepted_limit":50},
  "hits":[{
    "doc":4812,
    "id":"message:42",
    "_id":"message:42",
    "score":5.331,
    "sort":[1700000123,900,4812],
    "fields":{"title":"Пример","body":"..."},
    "_source":{"title":"Пример","body":"полный исходный текст"},
    "highlight":{"body":"...<em>поиск</em>..."}
  }]
}
```

`visited` — число реально просмотренных кандидатов. Неполный ответ всегда
содержит `partial:true`, `complete:false` и `terminated` со значением
`deadline`, `cancelled`, `verification_budget`, `expansion_budget` или
`shard_failure`. При `partial:false` тот же исход становится retryable 503.
При сборке с возможностью `stats` ответ также содержит внутренние счётчики
обхода.

## Агрегации

`aggs` — объект `имя → описание`, максимум 32 агрегации:

```json
{
  "filter":[{"field":"timestamp","from":1700000000}],
  "aggs":{
    "views":{"stats":{"field":"views"}},
    "channels":{"terms":{"field":"channel","size":20}},
    "per_day":{"histogram":{"field":"timestamp","interval":86400}},
    "unique_users":{"cardinality":{"field":"user_id","mode":"hll"}},
    "unique_users_exact":{"cardinality":{"field":"user_id","mode":"exact"}}
  }
}
```

| Вид | Параметры |
|---|---|
| `stats` / `count` | необязательное `field`; без поля считает документы |
| `terms` | `field`, необязательный `size` до `10000` |
| `histogram` | `field`, положительный `interval`, необязательный `offset` |
| `date_histogram` | `field`; `calendar_interval` (`1d`, `1w`, `1M`, `1q`, `1y`) либо положительный `fixed_interval` в миллисекундах; необязательный `time_zone` вида `+03:00` |
| `range` | `field`, массив `ranges` с включающей `from` и исключающей `to`; отсутствующая граница открыта; суммарно до 256 диапазонов |
| `cardinality` | `field`, `mode:"hll"` или `mode:"exact"`; HLL помечен `approximate:true`, exact никогда не деградирует молча |

Числовые агрегации требуют колонку числового или keyword-поля. Дробные границы,
сумма и корзины считаются по исходным значениям, а не по внутреннему
порядок-сохраняющему ключу. Для агрегации по элементам вложенного массива
добавьте `"over":"путь.группы"`. Именованные часовые пояса не принимаются:
для них нужна внешняя база tzdata, которой у движка нет.

Точная агрегация может разделить один большой сегмент на диапазоны
документов и использовать до `--threads=N` потоков. Деление включается только
для полного scan-path: word/phrase/must-not cursor, selective range leader и
дробная сумма сохраняют последовательный путь. Заголовочный fast path для
`range + count` тоже не делится, потому что уже отвечает за весь сегмент без
обхода документов. Deadline/cancel остаётся одним на запрос; остановленный
многопоточный ответ обязательно содержит `partial:true`.

## Распределённый поиск

Координатор запускается без собственного индекса:

```bash
svindb serve --shards=10.0.0.11:19300+10.0.0.12:19300,10.0.0.21:19300
```

Запятая разделяет шарды, `+` — реплики одного шарда. Координатор выбирает одну
реплику каждого шарда на весь запрос.

Дополнительные ключи запроса:

| Ключ | Значение |
|---|---|
| `scoring:"local"` | один проход, каждый шард использует местную статистику; умолчание |
| `scoring:"global"` | первый проход собирает статистику, второй выполняет поиск |
| `partial:true` | разрешить ответ без недоступных шардов |

Без `partial:true` отказ любого шарда даёт `503`. Распределённый hit содержит
пару `shard` и `doc`; локальные номера разных шардов не объединяются.

`from`/`size` применяются после общего слияния: шарды собирают окно от нуля до
`from + size`. Сортировка по полю, агрегации, `track_total_hits`, PIT и
`search_after` через сетевой координатор получают `400`, пока для них нет
корректного распределённого reduce. Эти возможности доступны локальному поиску.


### Чего координатор не делает

Координатор обслуживает **только поиск**. Точки, работающие с документами, —
`/_bulk`, `/_put`, `/_delete`, `/_flush`, `/_doc/{id}` и `/_mget` — на нём
отвергаются с `400` и объяснением: писать и читать по идентификатору надо у
шардов напрямую. Распределённый runtime одноиндексный; имя в пути здесь не
используется.

Прежде они обслуживались его собственным каталогом: запись уходила в пустой
индекс координатора и получала `200`, а чтение по `id` честно не находило
ничего. Клиент, отправивший данные не туда, узнавал об этом не отказом, а пустой
выдачей — когда-нибудь потом.

Раскладывать запись по шардам узел не умеет: это забота клиента. Правило
раскладки должно быть детерминированным и неизменным — число шардов после
создания не меняется.

`GET /_health` на координаторе добавляет блок `coordinator`:

```json
{"coordinator":{"shards":3,"replicas":5,"cooling":1}}
```

`cooling` — реплики, которые сейчас отвечают не первыми после отказа. Выдача при
этом приходит, и по ней бы никто не догадался, что часть копий лежит. Остальные
числа `/_health` у координатора нулевые по построению: своих документов у него
нет.

## Приём документов

### Добавление и замена

```bash
curl -s http://127.0.0.1:19300/catalog/_bulk \
  -H 'Content-Type: application/json' \
  -d '{"documents":[
    {"id":"m1","title":"Первый","views":10},
    {"id":"m2","title":"Второй","views":20}
  ]}'
```

`/_bulk`, `/_put` и `PUT /_doc/{id}` заменяют документ с тем же идентификатором.
Повтор явного идентификатора сохраняет одну живую версию; последняя запись
одного идентификатора внутри пачки побеждает. Отсутствующий идентификатор при
приёме получает автоматически сгенерированное непустое значение. Явная пустая
строка запрещена. Числовой и логический `id` родного тела преобразуются в текст.
В ES NDJSON идентификатор берётся только из action `_id`; source-поле `id`
остаётся обычными данными и не используется как ключ документа.

Для lease, revision и связанных служебных документов `/_put` принимает
условия compare-and-swap:

```bash
curl -s http://127.0.0.1:19300/catalog/_put \
  -H 'Content-Type: application/json' \
  -d '{
    "documents":[
      {"id":"queue:42","revision":18,"state":"running"},
      {"id":"attempt:42:3","revision":18,"state":"running"},
      {"id":"checkpoint:parser","revision":18,"state":"running"}
    ],
    "conditions":[
      {"id":"queue:42","field":"revision","equals":17},
      {"id":"attempt:42:3","field":"revision","equals":17},
      {"id":"checkpoint:parser","field":"revision","equals":17}
    ]
  }'
```

Все условия проверяются до записи под замками адресуемых `id`. Если хотя бы
одно не совпало, ответ — `409` с `conflict`, `id` и `field`, а ни один документ
не записывается. `equals:null` означает отсутствие живой версии. Поле условия
обязано существовать в схеме. CAS читает точную атомарную проекцию/source,
поэтому работает и при `store:false`, различает пустую строку, `null` и
отсутствие и не реконструирует значение из postings.

Когда одна логическая операция должна одновременно заменить документы и
погасить производные записи, используется `POST /{индекс}/_mutate`:

```json
{
  "documents":[
    {"id":"manifest","revision":2,"state":"running"},
    {"id":"relation-new","revision":1,"state":"running"}
  ],
  "deletes":["relation-old"],
  "conditions":[
    {"id":"manifest","field":"revision","equals":1},
    {"id":"relation-new","field":"revision","equals":null}
  ]
}
```

Успех возвращает количества `added` и `deleted` и `"durable":true`. Upsert и
delete записываются одной WAL-операцией и после аварийного restart
восстанавливаются вместе. Stale CAS даёт `409` до изменения любого документа.
Атомарность ограничена одним локальным индексом: coordinator отвергает
`/_mutate`, потому что общей транзакции нескольких шардов у него нет.

Пачка из нескольких документов попадает в одну WAL-запись с общей CRC и после
ACK целиком переживает restart. Автоматический порог сегмента не разрезает её
посередине. Эта атомарность относится к конкурирующим писателям, durable commit
и replay; она не превращает поиск в транзакционный MVCC-снимок. После restart
порт открывается только когда последний переигранный хвост опубликован, поэтому
первый успешный поиск уже видит подтверждённые до падения документы, а не ждёт
очередного таймера свежести.

### Что видно после замены

Буфер приёма участвует в поиске. Из него собирается **живой сегмент**, который
входит в состав наравне с обычными и пересобирается на каждом `refresh_interval_ms`
— не касаясь диска. Поэтому запись становится видимой поиску через срок
свежести, а не через сброс на диск, и `refresh_min_docs` можно держать высоким,
не платя за это свежестью.

Живой сегмент собирается заново целиком, и потому у него есть граница —
`live_max_docs`. Выше неё он не собирается: массовой загрузке нужна пропускная
способность, а не свежесть, и пересобирать миллион документов раз в секунду
дороже самой загрузки. Тогда видимость возвращается к прежнему правилу — по
сбросу на диск. Сколько документов видно поиску сверх опубликованного,
показывает `svindb_live_docs`; разница с `svindb_buffered_docs` — это то, чего
поиск сейчас не знает.

Замена при этом остаётся двумя событиями с разной задержкой: документ
становится долговечным на ACK, а видимым — на ближайшей публикации, живой или
дисковой. Между ними поиск отдаёт **прежнюю** версию, а не пустоту:

- поиск никогда не отвечает «не найдено» на документ, у которого есть живая
  версия, сколько бы замен ни прошло без публикации;
- поиск никогда не показывает версию старее той, что уже показывал;
- у одного `id` в выдаче не бывает двух версий, если не считать долей
  микросекунды внутри самой публикации, когда новая уже внесена, а прежняя ещё
  гасится.

Чего эти правила **не** дают: read-after-write для поиска в пределах одного
запроса. Сразу после ACK поиск ещё покажет предыдущую версию — до ближайшего
`refresh_interval_ms`, а при буфере больше `live_max_docs` до сброса на диск. Это
нормальный ответ, а не отставание, которое надо переждать. Клиенту, которому
нужна именно последняя версия **сразу**, её отдают `GET /{индекс}/_doc/{id}` и
`POST /{индекс}/_mget` — они смотрят в буфер приёма и не зависят ни от какой
публикации. Lease renewal при этом должен опираться на результат CAS: условие
сверяется с последней подтверждённой версией, а не с тем, что видно поиску.

Прежние версии гасятся в момент публикации, а не записи. Поэтому поле
`replaced` в ответе `/_put` считает только то, что погашено к моменту ответа, —
версии в буфере приёма. Общее число погашенного видно как `deleted` в
`/_health`.

Поля документа читаются по схеме индекса. Значение листа может быть строкой,
числом, bool или массивом скаляров. Вложенный путь `author.name` читается из
объекта `{"author":{"name":"..."}}`; nested-массивы раскладываются по slots,
включая nested-внутри-nested. Индексные slots внутренних уровней дают bounded
coarse-кандидатов, после чего lossless source verifier сохраняет связь
родительского и дочернего элемента. При превышении `max_verify` запрос получает
retryable `429`, а не неполный правдоподобный ответ.

JSON документа и его индексируемая проекция подтверждаются одной WAL-записью.
Внутреннее length-prefixed представление массивов не является API и не имеет
коллизии с пользовательским Unicode; наружу всегда возвращается исходный
JSON-массив. `enabled:false` хранит произвольное поддерево только в `_source`.
При `dynamic:"strict"` неизвестный путь проверяется на каждом уровне и
отвергается до WAL; при `dynamic:false` он сохраняется в source, но не
индексируется.

Офлайновый `svindb index` и HTTP-приём проходят через один и тот же план
вложенных путей, типизацию и укладку slot-групп. Поэтому один NDJSON-корпус не
меняет смысл после перехода между предварительной сборкой индекса и сетевой
заливкой.

Кроме родного тела принимаются Elasticsearch-совместимые формы:

```text
POST /messages/_bulk
{"index":{"_id":"m1"}}
{"title":"Первый","views":10}
{"delete":{"_id":"m2"}}
```

`POST` или `PUT /messages/_doc/m1` принимает один документ, а `DELETE` по тому
же пути гасит его. Действия NDJSON `create` и `update` отвергаются по документу:
движок не подделывает проверку существования и частичное обновление.

NDJSON возвращает `{"took":...,"errors":...,"items":[...]}` в исходном порядке.
Валидные `index`/`delete` выполняются независимо от ошибок соседних документов;
ошибка mapping или metadata получает item `status:400`. Повреждённый framing
отвергает запрос до первой записи. Недостаточное подтверждение реплик или отказ
WAL дают HTTP/item `503`. Успешный `index` возвращает `status:200` без поля
`result`: writer пока не различает created/updated для каждого элемента пачки.
`delete` возвращает `deleted`/200 либо `not_found`/404. Корневой NDJSON bulk с
маршрутизацией по нескольким индексам пока не поддержан в multi-index runtime.


В режиме `report` приём сохраняет годные значения и сообщает о потерях:

```json
{
  "added":2,
  "skipped":1,
  "skipped_docs":1,
  "bad_ids":["m2"],
  "skipped_first":["документ m2, поле views: значение не прочлось типом поля"],
  "unknown_fields":["viewz"],
  "unknown_total":1
}
```

`skipped` считает значения, `skipped_docs` — документы. Перечни примеров
ограничены 32 записями. Отсутствующее поле и `null` не считаются ошибкой.

По умолчанию `strict_ingest:"batch"`: любая потеря отвергает всю пачку до
записи в WAL и возвращает `400`. Режим `document` принимает только чистые
документы пачки, а `report` принимает всё годное и отвечает `200`. Старые
логические значения совместимы: `true` означает `batch`, `false` — `report`.

`POST /{индекс}/_validate` выполняет тот же разбор без записи и возвращает
`ok`, число документов и тот же отчёт о потерях. Текущая схема доступна через
`GET /{индекс}/_schema` или `GET /{индекс}/_mapping`.

### Чтение одного документа

```bash
curl -s http://127.0.0.1:19300/catalog/_doc/м1
```

```json
{
  "id":"м1",
  "_id":"м1",
  "found":true,
  "doc":4812,
  "fields":{"title":"Первый","body":"тело","views":10},
  "_source":{"title":"Первый","body":"тело","views":10,"meta":{"raw":true}}
}
```

Идентификатор берётся из пути и раскодируется из `%XX`, поэтому `PUT
/{индекс}/_doc/м1` и `/{индекс}/_bulk` с `{"id":"м1"}` означают **один и тот
же** документ.
Отсутствующий документ даёт `404` и `{"id":…,"found":false}`.

Если нужен только исходный объект, используйте
`GET /{индекс}/_doc/{id}?source_only=true`. Этот путь не просто скрывает
`fields` в JSON: он физически не открывает projection и stores объявленных
полей. На индексе с отключённым `_source` документ остаётся `found:true`, но
`_source` в ответе отсутствует. Негодное значение параметра получает `400`.

Отбора по `id` у поиска нет и быть не может: идентификатор лежит в своём
словаре сегмента и адресуется хешем, а не списком слов. Эта точка — тот
единственный способ прочесть документ, зная его `id`.

Ответ содержит `"buffered":true` вместо `doc`, когда документ уже принят и
долговечен, но ещё не опубликован. Это единственное место, где узел показывает
запись раньше, чем её увидит поиск: у поиска такой возможности нет, он идёт по
спискам опубликованных сегментов. Номер `doc` внутренний и меняется при
слиянии — долговременная ссылка клиента должна использовать `id`.

`_source` — исходный JSON-объект без flattening и синтеза отсутствующих полей.
Массив остаётся массивом, объект объектом, числа и bool сохраняют JSON-типы,
`null` остаётся в `_source`, а отсутствующий ключ отсутствует. `fields` —
типизированная проекция объявленных путей; она доступна и при `store:false`,
потому что строится из той же точной версии source, а не из колонки или
постингов. Внутренние поля `__svindb_*` никогда не выходят в schema, stats или
ответ документа.

### Чтение набора документов

```bash
curl -s http://127.0.0.1:19300/catalog/_mget \
  -H 'Content-Type: application/json' \
  -d '{"ids":["pool/a","pool/b","pool/нет-такого"]}'
```

```json
{
  "docs":[
    {"id":"pool/a","_id":"pool/a","found":true,"doc":4812,"fields":{"revision":7,"state":"idle"},"_source":{"revision":7,"state":"idle"}},
    {"id":"pool/b","_id":"pool/b","found":true,"buffered":true,"fields":{"revision":9,"state":"running"},"_source":{"revision":9,"state":"running"}},
    {"id":"pool/нет-такого","found":false}
  ]
}
```

Каждый элемент устроен как ответ `GET /{индекс}/_doc/{id}`, и порядок совпадает с
порядком запрошенных `id`: отсутствующий остаётся на своём месте с
`found:false`, а не выпадает из набора. Код ответа `200`, даже если не нашлось
ничего, — про каждый документ отвечает его собственное поле `found`.

Точка существует не ради экономии запросов. Набор читается по **одному**
снимку буфера приёма и состава сегментов, поэтому публикация, случившаяся во
время чтения, не может собрать ответ из разных поколений индекса: половина
набора до замены, половина после. Столько же отдельных
`GET /{индекс}/_doc/{id}` такой
гарантии не дают. Это не транзакция и не читающий snapshot всего индекса —
запись, легшая после снимка, в ответ не попадёт, как и у всякого читателя.

Пустой `id` запрещён, как и у `_delete`. Список длиннее 10 000 идентификаторов
отвергается с `400`.

### Удаление

```bash
curl -s http://127.0.0.1:19300/catalog/_delete \
  -H 'Content-Type: application/json' \
  -d '{"ids":["m1","m2"]}'
```

Ответ: `{"deleted":2}`. Пустой идентификатор запрещён. Удаление логическое:
физическое место освобождается фоновым обслуживанием.

### Принудительный сброс

```bash
curl -s -X POST http://127.0.0.1:19300/catalog/_flush \
  -H 'Content-Type: application/json' -d '{}'
```

`/_flush` — административная граница публикации, а не часть каждой мутации.
Запрос ждёт не дольше `flush_wait_ms`:

- `200 {"flushed":true}` — нужное поколение уже опубликовано;
- `202 {"flushed":false,"in_progress":true}` — срок ожидания истёк, работа
  безопасно продолжается в фоне;
- `503` — публикация или WAL отказали, приём остановлен до восстановления.

Текущее состояние видно как `flush_in_progress` в `/_health`. Вызывать
`/_flush` после каждого heartbeat нельзя: это снова создаст мелкие сегменты,
хотя сам HTTP-запрос теперь и не сможет зависнуть на минуты.

## Состояние и наблюдаемость

### `GET /_health` и `GET /{индекс}/_health`

Корневая точка multi-index процесса дешёво агрегирует живость и не раскрывает
внутреннее состояние каждого WAL:

```json
{
  "ok":true,
  "mode":"multi_index",
  "indices":2,
  "docs":1000000,
  "segments":4,
  "unhealthy_indices":[]
}
```

Подробное состояние выбранного индекса возвращает
`GET /{индекс}/_health`. В legacy-runtime это прежний корневой `GET /_health`:

```json
{
  "ok":true,
  "docs":1000000,
  "segments":4,
  "dead":120,
  "added":1000120,
  "deleted":120,
  "reload_failures":0,
  "reload_error":"",
  "mappings":8,
  "maps_limit":262144,
  "buffered":0,
  "wal":{
    "seq":1000120,
    "checkpoint":1000120,
    "replayed_adds":0,
    "replayed_puts":0,
    "replayed_deletes":0,
    "torn_bytes":0
  },
  "write_queue":{"pending":0,"limit":64},
  "compaction":{"pending_segments":0,"running_segments":0},
  "l0_admission":{"soft":8,"hard":24,"absolute":0,"baseline":0,"effective":0,
                  "throttled":0,"rejected":0},
  "flush_in_progress":false,
  "ingest_error":""
}
```

`ok:false` означает, что состав сегментов не перечитывается либо писатель
остановлен ошибкой. Поиск по последнему снимку состава при этом может ещё
работать, но узел следует вывести из балансировки. При неудачном перечитывании
новые записи получают временный отказ вместо ACK: сервер не увеличивает число
durable, но невидимых поиску операций. Фоновый пересмотр каталога остаётся
активным и сам возобновляет приём после успешного открытия состава.

`segments` считает всё, по чему идёт поиск, — включая живой сегмент, у которого
файлов на диске нет. Поэтому на узле с непустым буфером это число на единицу
больше числа каталогов сегментов, и обслуживанию такой сегмент не подлежит: он
исчезнет сам, когда буфер уедет на диск. Долг мелких сегментов надо смотреть по
`compaction.pending_segments`, а не по этому числу.

`l0_admission.absolute` — весь текущий compaction debt, `baseline` — наименьший
уровень, уже достигнутый этим процессом, а `effective` — новый рост поверх
него. При upgrade большой существующий backlog не блокирует ingest сам по себе:
soft/hard backpressure применяется к `effective`. По мере compaction baseline
снижается и не возвращается вверх, поэтому grandfathering не превращается в
постоянное разрешение снова наращивать долг.

### `GET /_stats` и `GET /{индекс}/_stats`

Корневая точка multi-index процесса возвращает агрегаты и компактную карту
индексов:

```json
{
  "version":"3.0.0-alpha.5",
  "mode":"multi_index",
  "uptime_seconds":11.716,
  "totals":{"indices":2,"docs":1000000,"deleted":120,"segments":4,"index_bytes":8454123},
  "indices":{
    "catalog":{"docs":900000,"deleted":100,"segments":3,"index_bytes":7000000,"writable":true},
    "audit":{"docs":100000,"deleted":20,"segments":1,"index_bytes":1454123,"writable":true}
  }
}
```

`GET /{индекс}/_stats` описывает выбранный индекс подробно. В legacy-runtime
этот же ответ доступен как корневой `GET /_stats`:

Чем узел является — то, что клиенту нужно один раз при подключении, а не на
каждой проверке живости:

```json
{
  "version":"3.0.0-alpha.5",
  "uptime_seconds":11.716,
  "dir":"/var/lib/svindb",
  "mode":{"read_only":false,"maintain":true,"wal":true,"coordinator":false},
  "shards":[],
  "threads":10,
  "schema":{"fields":5,"source_mode":"stored","mapping_transforms":0},
  "docs":1000000,
  "dead":120,
  "segments":4,
  "disk":{"index_bytes":8454123,"free_bytes":389122011136},
  "auth":{"enabled":false}
}
```

Отдельно от `/_health` намеренно: тот спрашивают много раз в секунду, и класть
в его ответ обход каталога значило бы платить за размер индекса на каждой
проверке живости. Размер каталога здесь считается с кешем в десять секунд.

`shards` у координатора — вложенные списки: внешний уровень задаёт номера
шардов, внутренний перечисляет равноправные реплики одного шарда.

`schema.source_mode` показывает фактически открытый статический режим:
`stored` или `disabled`. Он читается из persisted mapping, а не из параметра
последнего запроса, поэтому им можно проверять restart/rollover после CREATE.

`free_bytes` равно `null` на macOS: `statvfs` там объявляет счётчик блоков
32-разрядным, а `statfs` — структура с плавающей раскладкой. Отсутствие честнее
выдуманного числа.

### `GET /{индекс}/_inspect`

Из чего состоит занятое место. Тот же счёт, что печатает `svindb inspect
--json`, а не второй счёт того же:

```json
{
  "dir":"/var/lib/svindb",
  "docs":1000000,
  "segments":4,
  "live":{"segments":1,"docs":37},
  "bytes":8454123,
  "index_bytes":9914000,
  "free_bytes":389122011136
}
```

`bytes` — то, что занимают сегменты; `index_bytes` — весь каталог, включая WAL
и служебные файлы. Право административное: обход читает оглавления всех
сегментов, и точку можно спросить в цикле.

`live` — живой сегмент: он участвует в поиске, но на диске не занимает ни
байта, и в `docs`, `segments` и `bytes` не входит. Числа этой точки и `/_stats`
сходятся так: `stats.segments` = `segments` + `live.segments`. Без этой строки
два ответа расходились бы числом сегментов без всякого объяснения.

### `GET /{индекс}/_metrics`

Точка возвращает Prometheus text format. Основные семейства:

- `svindb_requests_total`, `svindb_responses_total`, `svindb_request_ms`;
- `svindb_docs_added_total`, `svindb_docs_deleted_total`;
- `svindb_docs`, `svindb_docs_dead`, `svindb_segments`;
- `svindb_buffered_docs`, `svindb_live_docs`, `svindb_flushes_total`,
  `svindb_segments_created_total`, `svindb_flush_ms`;
- `svindb_merges_total`, `svindb_merge_ms`,
  `svindb_compaction_pending_segments`, `svindb_compaction_running_segments`,
  `svindb_compaction_jobs_total`, `svindb_compaction_active_ms_total`,
  `svindb_compaction_paused_ms_total`, `svindb_compaction_query_preemptions_total`,
  `svindb_compaction_checkpoints_total`, `svindb_compaction_paced_bytes_total`,
  `svindb_compaction_paced_wait_us_total`, `svindb_compaction_eta_known`;
- `svindb_write_queue_pending`, `svindb_write_queue_highwater`,
  `svindb_write_queue_refused_total`;
- `svindb_resource_queue_active`, `svindb_resource_queue_limit`,
  `svindb_resource_queue_waiter_limit`, `svindb_resource_queue_waiters`,
  `svindb_resource_queue_wait_ms_total`;
- `svindb_workload_cpu_units_limit`, `svindb_workload_interactive_units_limit`,
  `svindb_workload_analytics_units_limit`, `svindb_workload_io_units_used`,
  `svindb_workload_io_units_limit`, `svindb_workload_latency_reserve_bytes`,
  `svindb_workload_wal_replay_bytes`, `svindb_workload_frozen_generations_limit`,
  `svindb_workload_background_io_bytes_per_second`,
  `svindb_workload_background_io_burst_bytes`,
  `svindb_workload_background_io_inflight_limit`;
- `svindb_wal_commits_total`, `svindb_wal_records_total`,
  `svindb_wal_commit_ms`, `svindb_wal_batch_records`,
  `svindb_wal_commit_failures_total`;
- `svindb_tombstone_ratio`, `svindb_searches_inflight`;
- `svindb_mmaps`, `svindb_mmaps_limit`;
- `svindb_wal_seq`, `svindb_wal_checkpoint`;
- `svindb_breaker_refused_total`, `svindb_shard_fallbacks_total`;
- `svindb_reload_failures`, `svindb_ingest_healthy`;
- `svindb_id_directory_ready`, `svindb_memory_internal_floor_bytes`;
- расход процесса: `svindb_build_info{version}`, `svindb_uptime_seconds`,
  `svindb_process_resident_bytes`, `svindb_process_virtual_bytes`,
  `svindb_process_cpu_seconds_total`, `svindb_process_threads`;
- место: `svindb_index_bytes`, `svindb_disk_free_bytes`.

Метрика, которой система не сообщает, **не печатается вовсе**: строка
`svindb_disk_free_bytes 0` означала бы «места нет», а не «не спросили».
Поэтому на macOS этой строки в выдаче не будет.

Вид `kind="get"` в `svindb_requests_total` и `svindb_request_ms` — чтение
документа по идентификатору. Отдельно от `kind="search"`: у него нет ни обхода
списков, ни ранжирования, и в общей гистограмме он сдвигал бы квантили вниз,
изображая узел быстрее, чем он есть.

`*_ms` и `svindb_wal_batch_records` — Prometheus histogram. Например, p95/p99
считаются через `histogram_quantile`, а не из среднего времени запроса.

## Настройки индекса

Настройки хранятся в `<индекс>/settings.json`. Приоритет:

1. аргумент запуска;
2. `settings.json`;
3. встроенное значение.

`PUT /{индекс}/_settings` — частичный patch:

```bash
curl -s -X PUT http://127.0.0.1:19300/catalog/_settings \
  -H 'Content-Type: application/json' \
  -d '{"refresh_interval_ms":500,"memory_budget_mb":512}'
```

| Настройка | Умолчание | Назначение |
|---|---:|---|
| `refresh_interval_ms` | `1000` | период проверки непустого буфера; `0` отключает таймер |
| `refresh_min_docs` | `1` | минимум документов для обычного timed refresh; `1` сохраняет прежнее поведение |
| `refresh_max_interval_ms` | `30000` | жёсткий возраст малой пачки до публикации |
| `live_max_docs` | `10000` | до скольких документов буфер приёма участвует в поиске; `0` выключает |
| `wal_group_commit_ms` | `2` | окно, в котором concurrent-запросы делят один durable `fsync` |
| `drop_flushed_page_cache` | `false` | разрешить DONTNEED для новых durable flush-сегментов; по умолчанию свежие данные остаются в page cache |
| `max_pending_writes` | `64` | запросов внутри write-path; следующий получает retryable `429` |
| `flush_wait_ms` | `5000` | предел ожидания `/_flush`; после него ответ `202`, работа продолжается |
| `flush_docs` | `1000000` | документов в сегменте приёма |
| `flush_mb` | `0` | предел буфера; `0` выбирается по доступной памяти/cgroup |
| `target_docs` | `1000000` | целевой размер сегмента по документам |
| `merge_at_once` | `8` | максимум сегментов одного слияния |
| `dead_fraction` | `0.20` | доля мёртвых документов для очистки |
| `grace_ms` | `2000` | задержка удаления заменённых каталогов |
| `merge_threads` | `0` | потоки слияния; `0` выбирается по числу ядер |
| `max_merged_mb` | `0` | максимальный размер слитого сегмента; `0` — решение движка |
| `floor_mb` | `0` | нижняя граница размера сегмента в tiered policy |
| `per_tier` | `0` | допустимое число сегментов яруса |
| `merge_policy` | `tiered` | `tiered`, широкий профиль `update_heavy` или совместимая плоская политика `flat` |
| `memory_budget_mb` | `256` | предел рабочей памяти запроса; `0` отключает breaker |
| `strict_ingest` | `batch` | `batch` — отвергнуть пачку; `document` — отвергнуть только плохие документы; `report` — принять годное и сообщить о потерях |

Неизвестный ключ и неверный тип дают `400`. Сначала новый файл атомарно
фиксируется на диске, затем меняется состояние процесса.

Практический профиль для служебного индекса задаётся измерениями конкретного
потока. Стартовая конфигурация, которая убирает flush из lease renewal и при
этом ограничивает задержку видимости:

```json
{
  "refresh_interval_ms": 500,
  "refresh_min_docs": 256,
  "refresh_max_interval_ms": 5000,
  "wal_group_commit_ms": 5,
  "max_pending_writes": 64,
  "flush_wait_ms": 1000,
  "merge_policy": "update_heavy"
}
```

Это не универсальные production-числа: `refresh_min_docs` выбирают по реальному
segment creation rate, а `refresh_max_interval_ms` — по допустимой задержке
поисковой видимости. Durability от обоих значений не зависит: ACK записи всё
равно выходит только после WAL `fsync`.

`update_heavy` сохраняет ярусные ограничения формата, но поднимает нижние
границы до 32 источников на проход, 32 сегментов на ярус, 16 МиБ floor и веса
возврата tombstone 3. Более высокие явно заданные пределы сохраняются. Это
профиль catch-up для накопленного долга; обычный `tiered` остаётся умолчанием
для append-heavy корпуса.

## Снимки

Разрешённые каталоги задаются в конфигурации сервера через `snapshot.allow` и
`snapshot.deny`. Пустой allow-list запрещает создание снимков.

```bash
curl -s -X POST http://127.0.0.1:19300/catalog/_snapshot/nightly \
  -H 'Content-Type: application/json' \
  -d '{"dest":"/srv/backups/svindb","fast":false}'
```

Если разрешён ровно один приёмник, `dest` можно не передавать. `fast:true`
уменьшает затраты CPU ценой размера архива.

Удаление снимка через HTTP намеренно отсутствует. Восстановление выполняется
только офлайн и только в пустой каталог:

```bash
svindb restore /srv/backups/svindb/nightly /srv/svindb-restored
```

## Авторизация, CORS и TLS

Конфигурация сервера передаётся через `--config=<файл>`:

```json
{
  "bind":"127.0.0.1",
  "port":19300,
  "threads":8,
  "cors":{"origins":["https://example.test"],"credentials":true,"max_age":600},
  "auth":{
    "roles":[
      {"name":"reader","privileges":["read"]},
      {"name":"writer","privileges":["read","write"]},
      {"name":"administrator","privileges":["read","write","admin"]}
    ],
    "users":[
      {"name":"operator","hash":"pbkdf2$...","roles":["administrator"]}
    ],
    "keys_file":"/srv/svindb/api-keys.json",
    "iterations":210000
  },
  "snapshot":{"allow":["/srv/backups/svindb"],"deny":[]},
  "workload":{
    "cpu":{"search_cpu_units":12,"interactive_max_units":8,"analytics_max_units":4},
    "memory":{"latency_reserve_mb":2048,"wal_replay_mb":64,"max_frozen_memtables":32},
    "compaction":{"policy":"query_first"},
    "io":{"background_mbps":64,"burst_mb":4,"max_inflight":2}
  }
}
```

Секция `workload` задаёт единый admission-профиль процесса. `search_cpu_units`
ограничивает общий бюджет уже исполняемого поиска, а `interactive_max_units` и
`analytics_max_units` — ширину одного запроса внутри этого бюджета. Эти permits
удерживаются до конца aggregation, hydration и serialization; они не являются
обещанием фиксированной доли физического CPU. `latency_reserve_mb` оставляет
память для control/point-read (runtime также применяет минимум 8% от cgroup
лимита), `wal_replay_mb` ограничивает хвост WAL до физического flush, а
`max_frozen_memtables` задаёт предел in-memory поколений до coalescing.

`io.background_mbps`, `io.burst_mb` и `io.max_inflight` образуют query-first
ограничитель фонового compaction I/O. В текущем одновузловом runtime одновременно
планируется не более одного compaction job на процесс; предел `max_inflight`
остаётся верхней границей для будущих maintenance lanes и публикуется в
`/_metrics`. Полоса относится к логическим порциям, поэтому фактические mmap,
readahead и writeback bytes дополнительно сверяются по cgroup/device counters.
Неизвестные ключи, отрицательные/нулевые небезопасные значения и политика,
отличная от `query_first`, отклоняются до открытия listener.

Авторизация включается автоматически, если определён хотя бы один пользователь.
Поддерживаются `Basic` и `ApiKey`. Пароль хранится только как PBKDF2-хеш:

```bash
svindb passwd 210000
```

API-ключ выдаётся один раз:

```json
POST /_security/api_key
{"name":"collector","roles":["writer"],"expires_ms":86400000}
```

Ответ содержит `id`, одноразовый `api_key` и готовое поле `encoded` для
`Authorization: ApiKey <encoded>`. Список ключей секретов не возвращает.

Для TLS соберите сервер с возможностью `tls`:

```bash
cargo build --release -p svindb-server --features tls
svindb serve /srv/svindb 19300 --tls-cert=cert.pem --tls-key=key.pem
```

Если TLS-флаги переданы бинарнику без этой возможности, узел отказывает в
запуске. Соединения координатора с шардами TLS не используют; защищайте их
доверенной сетью или внешним туннелем.

### Объявление полей

```text
title:2,body:1,status:keyword,views:int64,timestamp:date,
published_at:date:iso,payload:binary,place:geo_point,
reactions.emoji:keyword:slots,reactions.count:int32:slots,
embedding:dense_vector:768,embedding_sparse:sparse_vector
```

Поддерживаются `text`, `keyword`, `bool`, `int32`, `int64` (`long`), `float`,
`double`, `date`, `date:iso`, `binary`, `geo_point`, `dense_vector:<N>` и
`sparse_vector`.

Модификаторы:

- `nostore` — совместимый явный маркер отсутствия отдельной stored-копии.
  В обычном source-backed индексе пользовательские листья и без него не
  дублируются: `fields`, GET/MGET, CAS и highlight читают атомарную
  типизированную проекцию/`_source`. В source-disabled mapping тот же признак
  означает, что исходное значение после индексирования вернуть нельзя;
- `noindex` — не индексировать содержимое; оно остаётся в lossless `_source`
  либо только в отдельной копии при явном `store:true`.
- `slots` — поле лежит внутри массива, путь группы берётся до последней точки.

Пример: `raw:keyword:noindex`.

### Основные флаги `serve`

| Флаг | Назначение |
|---|---|
| `--bind=<адрес>` | адрес прослушивания |
| `--config=<файл>` | авторизация, CORS, snapshot paths и базовые параметры |
| `--read-only` | отключить запись и обслуживание |
| `--no-maintain` | оставить запись, отключить merge/reclaim |
| `--no-wal` | не использовать WAL; снижает долговечность |
| `--warm` | последовательно прогреть метаданные открытых индексов |
| `--threads=N` | максимум потоков одного поиска |
| `--fields=<спецификация>` | схема по умолчанию для `PUT /{индекс}` с пустым телом; в legacy — схема нового пустого индекса |
| `--single-index` | явно создать новый каталог прежнего одноиндексного формата |
| `--multi-index` | устаревший совместимый флаг; новые каталоги и так multi-index |
| `--max-indices=N` | предохранитель числа одновременно открытых индексов; по умолчанию 64 |
| `--flush=N` | переопределить `flush_docs` на этот запуск |
| `--target=N` | переопределить `target_docs` |
| `--refresh-ms=N` | переопределить интервал свежести |
| `--merge-at-once=N` | ширина слияния |
| `--merge-threads=N` | потоки слияния |
| `--dead-fraction=F` | порог очистки |
| `--grace-ms=N` | задержка удаления старых каталогов |
| `--allow-low-map-count` | предупредить вместо отказа при низком mmap-limit |
| `--shards=<список>` | режим координатора |
| `--tls-cert`, `--tls-key` | TLS для клиентского HTTP |

Без явного каталога данные располагаются в `data` рядом с бинарником, а не в
текущем каталоге процесса.

Аргумент, начинающийся с дефиса и не узнанный разбором, печатает подсказку и
завершается с кодом `2`. Узел он **не поднимает**: прежде любой неузнанный
аргумент — включая `--help` — брал writer-lock на каталог `data` и начинал
слушать порт, ни словом об этом не сказав.

### Обслуживание формата

- `check` работает только на чтение; `--full` пересчитывает содержимое всех
  файлов и кусков контейнера. Смотрит он на диск: принятое и ещё не сброшенное
  живёт в буфере и в журнале, и в проверку не входит — по построению, а не по
  недосмотру.
- `inspect` объясняет расход диска и памяти; `--plan` оценивает новую раскладку.
- `pack` собирает неизменяемые части старого сегмента в `seg.dat`.
- `unpack` раскладывает `seg.dat` обратно по файлам.
- `bloom` перестраивает фильтры идентификаторов.
- `wal` показывает записи и точку восстановления журнала.

## Коды ответа

| Код | Значение |
|---:|---|
| `200` | операция выполнена |
| `201` | снимок создан |
| `400` | неверное тело, схема, поле, курсор или режим узла |
| `401` | нет или не приняты учётные данные |
| `403` | недостаточно прав либо запрещён путь снимка |
| `404` | снимок или ресурс не найден |
| `405` | метод для маршрута не поддерживается |
| `409` | конфликт при создании снимка |
| `413` | тело запроса превышает предел |
| `429` | превышен query breaker, очередь записи, общий cgroup-aware бюджет HTTP-тел либо лимит попыток входа; retryable-ответ требует backoff |
| `503` | ошибка писателя, настройки на диске или обязательного шарда |

Клиент должен считать `partial:true`, `ok:false`, `skipped` и `failed`
частью контракта, а не диагностическими комментариями: они означают неполный
результат или деградацию, требующую явного решения вызывающей стороны.
