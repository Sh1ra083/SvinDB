# Перенос схем в SvinDB

Этот документ описывает общие правила переноса схем из документных поисковых
систем. Он не привязан к конкретному проекту, набору индексов или локальной
структуре каталогов.

## Поддерживаемые типы

| Исходный смысл | Тип SvinDB | Примечание |
|---|---|---|
| анализируемый текст | `text` | полнотекстовый поиск, позиции и фразы |
| точная строка с lowercase | `keyword` | родной тип; exact term после приведения регистра |
| регистрозависимая строка | `keyword:exact` | без изменения Unicode-регистра |
| 32-битное целое | `int32` | знаковый диапазон `i32` |
| 64-битное целое | `int64` или `long` | оба имени равнозначны |
| дата как Unix timestamp | `date` | значение передаётся **целым числом**; строка ISO отвергается |
| дата строкой ISO-8601 | `date:iso` | принимает `2024-01-15T10:00:00Z`; внутри миллисекунды |
| логическое значение | `bool` | `true` или `false` |
| 32-битное вещественное | `float` | значение должно быть конечным |
| 64-битное вещественное | `double` | значение должно быть конечным |
| плотный вектор | `dense_vector:N` | `N` задаёт размерность |
| разреженный вектор | `sparse_vector` | пары «признак — вес» |
| непрозрачные байты | `binary` | значение в Base64; регистр значим |
| точка на земле | `geo_point` | объект, строка или массив; см. ниже |

### Почему у даты две записи

У `date` в колонке лежит то целое, что прислали, и это чаще всего секунды.
Если бы тот же вид разбирал ещё и строки ISO, поле с секундами получило бы
значения, отличающиеся в тысячу раз, — и узнать об этом было бы неоткуда:
отбор по диапазону просто перестал бы находить. Поэтому единица измерения
входит в объявление.

### Двоичное поле

Значение приходит и отдаётся в Base64 обычного алфавита с выравниванием.
Регистр **значим**: `AQAAAB8ABbBc` и `aqaaab8abbbc` — разные байты. URL-безопасный
алфавит (`-` и `_` вместо `+` и `/`) не принимается: он даёт другие байты, и
принять оба молча значило бы, что одно написание значит разное.

Ищется точным совпадением, как ключевое слово. Разбора на слова, ранжирования и
фраз у него нет.

### Точка на земле

Принимается тремя записями, и все три равнозначны:

```json
{"место": {"lat": 55.7558, "lon": 37.6173}}
{"место": "55.7558,37.6173"}
{"место": [37.6173, 55.7558]}
```

Порядок в массиве обратный тому, что в строке, — так пишет Elasticsearch, и
перепутать их легко. Пределы проверяются: широта ±90, долгота ±180, за ними
отказ, а не приведение к границе.

Объявление заводит две колонки-спутника, `<поле>.lat` и `<поле>.lon`, и рамка
спрашивается обычным отбором по ним:

```json
{"filter": [{"field": "место.lat", "from": 55, "to": 56},
            {"field": "место.lon", "from": 37, "to": 38}]}
```

**Чего у гео нет:** агрегаций по расстоянию, полигонов, геохешей.

Самостоятельный контейнер `object` полем не является: объявляются его листья.

## Вложенные поля

Путь с точками объявляется как обычное имя поля:

```text
author.name:keyword
```

Документ при этом присылается **как есть** — движок сам спускается во
вложенность:

```json
{"id": "1", "author": {"name": "Аня"}}
```

## Массивы объектов

Метка `slots` объявляет, что поле лежит внутри массива. Массив — всё до
последней точки пути:

```text
reactions.emoji:keyword:slots
reactions.count:int32:slots
```

Документ присылается как есть:

```json
{"id": "1", "reactions": [{"emoji": "up", "count": 3},
                          {"emoji": "fire", "count": 1}]}
```

Условие «сошлось в одном элементе» пишется через `slots`:

```json
{"query": {"must": [{"slots": {"group": "reactions", "all": [
  {"field": "reactions.emoji", "terms": ["up"]},
  {"range": {"field": "reactions.count", "from": 3, "to": 9999}}]}}]}}
```

Такой запрос найдёт документ выше и **не найдёт** документ, где `up` стоит у
одной реакции, а счётчик не меньше трёх — у другой. Без `slots` условия
проверялись бы по документу целиком, и разница пропала бы.

### Массив скаляров

Обычное поле принимает как одно значение, так и JSON-массив скаляров того же
типа. Дополнительная схема и обёртка `{value:...}` не нужны:

```text
теги:keyword:exact
идентификаторы:int64
```

```json
{"id":"1","теги":["один","два"],"идентификаторы":[42,99]}
```

Каждое значение получает отдельный exact posting, поэтому `term`/`terms`
находит документ по любому элементу. Внутреннее представление кодируется
длинами, а не разделителем: строка с `U+001F` и два элемента физически
различны. `GET`, `_mget` и search `_source` возвращают исходный массив с
исходными JSON-типами.

Массивы объектов внутри других nested-массивов принимаются из Elasticsearch
mapping без flattening. Для прямого запроса по внутреннему nested используются
его slots; запрос, связывающий условие родителя с условием ребёнка, получает
coarse-кандидатов по postings и точную parent-child проверку по `_source`.

**Поле внутри массива нельзя читать номером документа.** Агрегация по нему
требует `"over": "<путь массива>"`, а сортировка и отбор по нему отказывают с
объяснением: колонка адресуется ординалом элемента, и прочитанное номером
документа значение принадлежало бы чужой ячейке.

## Многозначность

Многозначное поле нельзя безоговорочно сводить к первому элементу: это меняет
поиск, агрегации и сортировку. Выбор зависит от смысла данных:

- независимые значения одного поля передаются как несколько значений;
- значения внутри массива объектов дополнительно связываются слотами;
- если бизнес-контракт действительно разрешает только одно значение, лишние
  элементы лучше отвергать на стороне преобразователя, а не молча отбрасывать.

## Мультиполя

Elasticsearch-конструкция `fields` компилируется автоматически. Например,
`title` как `text` и `title.raw` как `keyword` читают одно исходное значение;
клиент не дублирует его в документе. В родной компактной схеме то же по-прежнему
объявляется двумя полями и требует двух значений, потому что там нет mapping
tree, из которого можно вывести source-path.

## Совместимость с Elasticsearch

Приём принимает построчное тело `_bulk` и точку `/{индекс}/_doc/{id}`; поиск
понимает `match`, `term`, `terms`, `range` с `gte`/`lte`/`gt`/`lt`,
одноуровневый `bool`, `nested`, `exists`, `_source:true|false`, `size`, `from`
и стандартный `sort`. Свои дополнения
(`slots`, `phrases`, `sparse`, `vector`, `translit`, `ids`) кладутся в ключ
`svindb` рядом с `query`.

При создании индекса поддержаны `mappings._source.enabled:false` и статический
`settings.index.mapping.source.mode:disabled`. Они не меняют индексируемость
полей: `index:true` продолжает строить postings/columns/vectors, а `store:true`
отдельно решает, можно ли вернуть значение без source. Source mode сохраняется
в mapping, наследуется rollover и не меняется через `/_settings`.

В режиме `disabled` исходный объект, `null`, неизвестные `dynamic:false` поля и
`enabled:false` поддеревья не сохраняются. GET/MGET/search возвращают ID и
явные stored fields без `_source`. Highlight требует `store:true`; запрос,
который связывает уровни nested и нуждается в source-verifier, получает точный
`400`. `synthetic`, includes/excludes и фильтрация source не изображаются
частично и также отвергаются.

Тело с приметами обоих языков отвергается: смешивать их нельзя.

**Неизвестный ключ запроса — отказ.** Привычное `{"filter":[{"field":"views",
"gte":1000}]}` в родном диалекте прежде вырождалось в «у поля есть значение» и
отвечало двумястами; теперь оно называет ключ.

## Строгий приём

**По умолчанию пачка с потерями отвергается** — ответ 400, и виноватые
документы названы своими `id`. Прежде она отвечала двумястами, а о потерях
говорилось только в теле: клиент с `raise_for_status()` или `curl -f` терял
данные молча.

Мягкое поведение включается настройкой:

```bash
curl -X PUT http://127.0.0.1:8080/_settings \
  -H 'Content-Type: application/json' \
  -d '{"strict_ingest":"report"}'
```

Значения: `batch` (по умолчанию — отвергнуть всю пачку), `report` (принять
годное, о потерях сказать в теле). Логические `true` и `false` принимаются как
синонимы `batch` и `report`.

Ответ приёма при потерях несёт `skipped` (сколько значений), `skipped_docs`
(сколько документов), `bad_ids`, `skipped_first` и `unknown_fields`.

## Проверка документа до заливки

```bash
curl -X POST http://127.0.0.1:8080/_validate \
  -H 'Content-Type: application/json' \
  -d '{"documents":[{"id":"1","цена":"не число"}]}'
```

Прогон идёт **тем же** разбором, что и настоящий приём, но ничего не пишет.
Ответ несёт `ok` и те же счётчики потерь.

Схему узла можно спросить:

```bash
curl http://127.0.0.1:8080/_schema
```

## Проверка переноса

Перенос считается подтверждённым только после проверки на представительном
корпусе. Минимальный набор сравнений:

1. одинаковое число принятых и отклонённых документов;
2. одинаковые результаты точных, полнотекстовых, фразовых и вложенных запросов;
3. одинаковые границы числовых фильтров, сортировка и агрегации;
4. отсутствие неизвестных и молча пропущенных полей;
5. повторное открытие индекса и `svindb check --full` без ошибок.

Синтетический корпус должен воспроизводить не только типы, но и реальную
заполненность, многозначность и распределение размеров. Корпус, где заполнено
каждое объявленное поле, обычно измеряет другую задачу и даёт неверное
представление о памяти и скорости.

## Чего движок не умеет

Названо здесь, а не умолчано: несделанное, о котором не сказано, обнаруживается
на боевых данных.

- **Range, sort и агрегации по корневому массиву чисел.** Exact `term/terms`
  работают по каждому элементу, но документная колонка не выбирает за клиента
  min/max и не выдаёт ложный scalar. Для таких операций используйте nested
  объект с явной семантикой элемента либо отдельное агрегатное поле.
- **Вложенные агрегации** (`aggs` внутри корзины), `percentiles`, `top_hits`,
  `filters`, `terms.order` по метрике, `composite`.
- **Гео-агрегации, полигоны, геохеши, радиус и сортировка по расстоянию.**
  Доступен прямоугольный фильтр через служебные поля `.lat` и `.lon`;
  остальные геооперации пока не входят в публичный API.
- **Именованные часовые пояса.** Только постоянное смещение вида `+03:00`.
- **Правка схемы на живом узле.** Поля объявляются при запуске; изменение
  требует перезапуска.
- **`create` и `update` в построчной пачке.** Отвергаются по документу с
  объяснением: узел дёшево не знает, есть ли уже такой документ, а частичное
  обновление требует чтения-правки-записи, которых у движка нет.
- **Динамическое добавление полей.** `dynamic:true` и `runtime` требуют
  изменения живой schema и отвергаются. Поддержаны честные `strict` и `false`.
- **Произвольные анализаторы и normalizer chains.** В mapping поддержаны
  `standard` и normalizer из одного `lowercase`; остальные цепочки получают
  `400`, а не молчаливую подмену.
